# Durable operator settings and case evidence integration

Date: 2026-10-11. Worker-3 scope. This document distinguishes tested local backend persistence from pending browser/operator acceptance. No live sensor evidence was generated.

## Design and security boundaries

`backend/darkfleet/config/settings.py` is environment-owned runtime configuration: API bind, provider URLs, credentials, CFAR, matching rules, and AIS inputs. **None of these keys are exposed or changed by the new operator settings API.** User-adjustable preferences are strictly limited to three System-panel display booleans:

| Persisted preference | Actual UI effect | Explicitly NOT changed |
| --- | --- | --- |
| `show_provider_details` | Show/hide **optional healthy-provider** descriptive text; failure causes remain visible | Provider probe, provider status, unavailable/error messages, failure severity, credentials, egress |
| `show_keyboard_reference` | Show/hide keyboard shortcut reference section | Global shortcut registrations or application key handlers |
| `show_provenance_summary` | Show/hide **supplementary explanation only** beneath mandatory SYSTEM provenance | The Scan/Stage/Stream/Raster indicators, SAR/AIS source labels, exports, audit evidence |

All three default to `true`. Hiding optional content is presentation-only. **Even with all three false**, the UI keeps the actual provider statuses (including UNAVAILABLE and failure reasons) and the mandatory Scan/Stage/Stream/Raster source-status indicators. A focused DOM regression proves this; a saved setting never suppresses sensor provenance or evidence. A saved preference is scoped to **the API's configured local `data_dir`**; it is not silently written to a browser profile or source config. The source of truth is SQLite `operator_settings.sqlite3` in that data root. Its single row has an integer revision; SQLite `BEGIN IMMEDIATE`, transaction commit and synchronous FULL enforce atomic persisted revisioned writes across concurrent application processes. GET when unset returns revision `0` with defaults, not an invented prior edit. `PUT` requires exact `expected_revision` and all three booleans; `POST /reset` requires the revision and creates another durable revision with defaults. Any concurrent stale write returns **409 OPERATOR_SETTINGS_REVISION_CONFLICT**; unknown keys or malformed values are 422.

The new backend router `backend/darkfleet/api/operator_settings.py` must be mounted by the prime in `backend/darkfleet/api/app.py`, which is prime-owned. No generalized arbitrary-key settings dictionary, provider API key editor, risk-control override or egress toggle exists. The client `src/api/operatorSettings.ts` validates the exact response shape before accepting it. The UI in `src/command/SystemPanel.tsx` has controls backed by GET, PUT, reset POST, reload GET and explicit revision/error states. Save is disabled until a verified response and a change; a 409 disables writes until Reload; a request failure is not shown as a success. Checkboxes only change effective panel presentation after acknowledged server commit; unsaved drafts remain drafts.

## Case title and binary evidence extension

Worker-2 owns the backend case title and attachment contracts; worker-3 integrated **only frontend** after the endpoints were available. Case rename is `PUT /api/investigations/{case_id}` with `{title}`; the backend persists only the title, never silently edits linked scan identity. Notebook shows a Rename case editor and uses the returned case record to update its list. Deleting a case requires a confirmation that specifically warns the operator about the permanent deletion of **all attached binary bytes**, while linked source-scan evidence is retained.

The new `src/api/investigationAttachments.ts` and `src/reports/InvestigationAttachments.tsx` implement the case-specific binary archive: safe filename input, a real raw-file `POST` (not JSON or a fictional multipart endpoint), a list GET, per-attachment direct-byte downloads, and confirmed DELETE. The backend stores bytes and metadata in one transaction under the case. Supported filename extensions: PDF, PNG, JPEG, TXT, CSV, JSON; exact size limit **8 MiB per file**, backend additionally caps 32 files and 64 MiB per case. The upload client sends `X-Attachment-Filename` and a matching `Content-Type`. It refuses path-like names and oversize files before transport. The server independently validates signatures and limits; frontend MIME checks never replace backend verification.

Every listed record must have `OPERATOR_ATTACHMENT_NOT_SENSOR_EVIDENCE`, a 64-character lowercase SHA-256 and a **same-case, exact local download URL**; malformed list counts, foreign URLs, unsupported MIME and forged sensor provenance are rejected. The persisted checksum is displayed; the bytes-download endpoint rechecks SHA-256 on the server. Investigation JSON/PDF reports include an **operator-only attachment metadata manifest** (filename, size, SHA-256) without embedding uploaded file bytes as satellite evidence. A failed inventory read is not rendered as "zero attachments." If POST/DELETE has succeeded but a subsequent list GET fails, the UI clearly states the mutation was committed and instructs reload, **not blind resubmission**. Transport failure after a POST is explicitly an *unverified outcome*, not a fabricated failure or success receipt. Delete requires confirmation.

## Operational limitations

General server config remains environment-administered; this feature intentionally does not expose tokens, alter live feeds, enable providers, or change detection behavior. There is no arbitrary settings marketplace. Case attachments are **operator-provided evidence documents**, not a replacement for verified SAR/AIS inputs. Production `data/` is untouched by these tests. User-owned ports 8000/5174 remain outside our isolated run. Worker-2 backend source and the shared application router were not edited by worker-3.
