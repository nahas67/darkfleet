## Scoped bug and repair: ambiguous persistence after re-fetch failure

**Before:** In `InvestigationGeometryPanel.tsx`, after the server successfully handled geometry `POST`, `PUT` or `DELETE`, the code immediately made another `GET` for the refreshed geometry list. If the GET failed, the shared catch displayed a generic error while leaving the editing draft or delete confirmation in place. This made an already persisted mutation look like a failed write, inviting duplicate submissions or repeated deletes.

**After:** New `src/reports/commitAndReconcile.ts` explicitly separates the two independent operations: a rejected write throws and **does not** report persistence; a confirmed write followed by successful GET returns `CONFIRMED` with the server list; a confirmed write followed by failed GET returns `PERSISTED_LIST_UNVERIFIED` with the original failure reason. The panel clears a committed draft/delete confirmation, does not present stale geometry counts as measured empty, displays an explicit persisted-but-unverified status instructing **retry list, not submit again**, and retains the existing reload control. A loading indicator is displayed during reconciliation. Three targeted deterministic tests prove write→GET ordering, server-commit+GET-failure recognition, and rejected-write behavior; mock results are unit test fixtures, **not** a claimed real server receipt.

The existing provenance declaration `OPERATOR_ANNOTATION_NOT_SENSOR_EVIDENCE` is unchanged. No missing target, AIS fix, acquisition, or binary attachment is invented.
