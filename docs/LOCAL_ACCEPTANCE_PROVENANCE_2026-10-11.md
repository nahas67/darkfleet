## Proven closeBundle async ordering — actual installed runtime

The question was whether `build-tools/buildIdentity.ts` running as the second `closeBundle` hook can hash an incomplete tree while `vite-plugin-cesium@1.2.23` is still copying Cesium assets.

1. **Installed toolchain:** Vite **8.3.2**, Rolldown **1.2.12**. The installed `node_modules/rolldown/dist/shared/define-config-*.d.mts` declares `sequential?: boolean` deprecated because these hooks **always execute sequentially**. The native hook binding forwards `order` metadata; `vite.config.ts` registers `cesium()` before `darkfleetBuildIdentity()`.
2. **Actual Cesium implementation:** `node_modules/vite-plugin-cesium/dist/index.mjs:75-88` has an `async closeBundle` that `await`s five `fs.copy` operations (Assets, ThirdParty, Workers, Widgets, Cesium.js). This plugin catches copy failures and only prints `copy failed`, so hook ordering by itself does **not** guarantee successful scientific/UI runtime copying.
3. **Independent native bundler test:** `build-tools/test_acceptance_provenance.py` launches installed Rolldown on a tiny temporary module with two plugins. The first `async closeBundle` waits 45 ms and writes a Cesium-like binary. The second reads that binary and refuses an early/missing file. Both *ordinary declaration order* and `{ order: 'post', sequential: true, handler }` variants **PASSED**, producing exact events `copy-start → copy-done → manifest-start → manifest-done`. Both are genuine `await bundle.close()` executions; no mocked hook runner.

**Verdict:** `async closeBundle()` in registered order is sequential on this installed production Rolldown. `order:'post'` is supported and adds priority over other ordinary hooks; `sequential:true` is accepted but deprecated/redundant with this installed engine. This proof does not establish behavior for a different Rolldown/Vite version, nor replace a full clean Vite build/release verifier run.

**Copy-failure residual:** `build-tools/release_build_verifier.py::check_cesium_copy` already compares the installed package's expected Cesium trees and Cesium.js against physically emitted `dist` and the served preview, supplementing the physical-tree manifest comparison. The package's swallowed `fs.copy` exception would therefore fail the checked release if required bytes were absent. A build log alone is never a passing receipt. The local release receipt at HEAD `2abf3de` previously passed **20/20** checks across **393 emitted files including 390 Cesium resources**; `b5bdc67` is a later documentation HEAD and must have its own current HEAD/preview receipt. Do not treat historical preview bytes as a build of the current HEAD.

**Tested current supported behavior:** The new TestClient negative checks verify that an operator-created case and note saying `calibrated Sentinel-1 VV, real AIS` stays `operator_material` with `OPERATOR_ANNOTATION_NOT_SENSOR_EVIDENCE`, `NO_SCAN_LINKED`, null sensor metadata and no sensor targets. An attempt to inject `sensor_evidence`, `calibration_verified` or `synthetic` through typed investigation/annotation POST fields returns 422. Non-live fixture scan IDs are rejected as unknown by an empty authoritative scan store (404).

**In-flight binary attachment route:** During the audit, another worker introduced **uncommitted** `backend/darkfleet/api/investigation_attachments.py`, schema changes in `api/investigations.py`, and operator presentation settings. The independent TestClient test uploaded a JSON file whose actual bytes falsely claim `runtime_mode='REAL'`, `synthetic=false`, `calibration_verified=true`, Sentinel-1 origin, and `REAL_AIS` observations. The real temporary API accepted it solely as `OPERATOR_ATTACHMENT_NOT_SENSOR_EVIDENCE` with byte-exact download, rejected a spoofed `.tif` attachment as unsupported (415), and produced `NO_SCAN_LINKED` with empty sensor records before and after application restart. **This is a meaningful negative test of the new path, but it is not a production acceptance of concurrently uncommitted code.**

The new route bounds each raw upload at 8 MiB, restricts extensions, checks binary signatures/UTF-8, stores blobs and SHA-256 in transactional operator SQLite, and uses a separate `OPERATOR_ATTACHMENT_NOT_SENSOR_EVIDENCE` response type. Its route is nested under investigations. The new `operator_settings.py` declares three presentation booleans only and explicitly excludes scientific thresholds, credentials and provider/runtime configuration. Verify these constraints after workers finalize/commit, especially any report integration, downloads, symlink/filename cases, revision-conflict behavior, and UI wiring. Do not infer real calibrated SAR/AIS from a SHA-256 of arbitrary operator-supplied bytes: a checksum proves byte identity, **not sensor origin or radiometric validity**.

**Additional provisional UI/source review:** `src/reports/InvestigationAttachments.tsx` explicitly displays operator provenance and rejects an unverified attachment inventory; `src/api/investigationAttachments.ts` checks the exact server provenance literal and case-owned URL. Current `investigation_reports.py` places *attachment receipt metadata* in `operator_material.attachments`, without inserting the binary BLOB into `sensor_evidence`. The report does **not** reread and hash the BLOB when exporting a receipt; download does recheck size and SHA-256, rejecting corrupt data with HTTP 409. Present the report digest as a **recorded checksum**, not as a fresh independent verification of the underlying attachment bytes. In `SystemPanel.tsx`, the optional `show_provenance_summary` setting can hide the Scan/Stage/Stream/Raster summary; it must not suppress mandatory source warnings or change record classification. The inspected source shows no P0 route that promotes uploads to scanned/calibrated evidence. This finding is bounded to in-progress source review and the described TestClient operations.

**Historical persisted REAL boundary:** `backend/darkfleet/investigation_reports.py::_scan_source` labels an already persisted record `PERSISTED_REAL` when the RunStore returns one with `runtime_mode='REAL'` and `synthetic is False`. The existing `backend/tests/test_investigation_reports.py` constructs such records with `mark_synthetic`; this verifies software projection/whitelisting, not authenticated remote acquisition. A locally forged record with those fields is not independent scientific proof. `PERSISTED_REAL` must be interpreted as *persisted with expected application metadata*, with acquisition authentication/calibration as a **separate external gate**. Operator attachments must never be injected into RunStore nor scanned as such records.
