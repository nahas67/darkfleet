# DarkFleet API contract and route verification — 2026-10-11

## Verified scope and coverage

- `create_app().openapi()` reports **61 paths / 73 operations**. The separate liveness route is `GET /health`; the rest are scoped to `/api`.
- `backend/tools/route_reachability.py --json` discovers **40 frontend route groups**: 39 caller-reachable and 39 product-reachable. The sole orphan is `GET /api/scans/{scan_id}/raster`, already classified **REDUNDANT** (the layer-specific raster endpoints are called); there are **zero unexplained orphans**. This is static import/literal reachability, not a browser action proof.
- `POST /api/scans` validates the provider and selected product, searches a real STAC provider for coverage, submits a real job to `ScanRunner`, and invokes the canonical `darkfleet.pipeline.run_scan` via `_scan_work`. No fake provider or completed result is generated by these routes. The internal scene is a selected candidate; a pinned `sceneId` is passed into the canonical pipeline for exact matching.
- `GET /api/scans/{id}` returns the current runner state or a persisted record. `GET /api/scans/{id}/events` replays actual runner events and ends after a terminal event; it has a bounded timeout. The API has **no scan cancellation operation**, and `ScanRunner` exposes no cancellation method. A restarted process can reload an unfinished job without an active worker, so stale in-flight recovery is a separate jobs-layer limitation; it is not verified closed here.
- Request boundary checks verified: invalid POST AOIs are HTTP 422; malformed/nonfinite, inverted or out-of-range `/api/scenes?bbox=` are HTTP 400; unknown providers are refused without arbitrary destination URLs. Configured STAC endpoint URLs remain a deployment trust boundary. This review did not claim comprehensive enforcement against malicious operator configuration.

## Corrections in this scope

1. The HTTP API previously redacted the top-level `ScanStateResponse.error`, while stage history and SSE frames could expose provider exception text containing signed source URLs. Public history details and SSE frames now redact credential-like values without rewriting the underlying persisted forensic/job record.
2. Structured `RealDataUnavailableError` bodies could serialize nested provider metadata and suggestions containing access tokens. `app.py` and `routes.py` now scrub credential-bearing strings and named fields recursively while preserving normal status, HTTP codes, and nonsecret detail values.
3. The provider health probe assumed an HTTP-200 `collections` field was iterable. Malformed responses such as `{"collections":null}` are now reported as `UNAVAILABLE` with an explicit invalid-document error instead of raising a server exception.
4. Follow-up jobs-layer correction: `ScanRunner._record_failure` now removes credential-like query parameters, JSON key/value secrets, and authorization header credentials **before** storing the failure, appending the terminal stage event, notifying subscribers, writing state JSON, and logging the diagnostic. Nonsecret failure text and the canonical `failed_at` stage are preserved. The source exception is not edited.

## Outstanding acceptance gaps

- Scan cancellation and explicit handling of jobs recovered in an unfinished stage need coordination with the canonical jobs subsystem. They cannot be represented honestly by an API-only status change.
- The jobs-layer failure-exception path is now scrubbed before persistence and logging. Ordinary success-stage details are still recorded verbatim; producers must not include signed URLs in stage descriptions. This review does not claim complete protection against arbitrary sensitive information in application logs or third-party library output.
- `_observations` propagates unknown detection length and uncertainty as `None`. Its consumer in `darkfleet.tracks` formerly attempted `float(None)`; the tracks owner is implementing nullable track points, while the generated advanced contract is owned separately. Full `/api/tracks` verification depends on their integrated changes.
- Re-run the complete API/integration/contract suite and frontend generated-type check after the coordinated georeferencing, tracks, and contract changes settle. Do not claim a full green gate based solely on the focused passes above.
